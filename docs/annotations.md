# In-Code Annotations

pcke supports in-code annotations that let developers embed knowledge directly
in source files.

## Syntax

### `@pcke-rule`

Declares a project rule or constraint:

```go
// @pcke-rule: All database access must go through the repository layer.
```

```python
# @pcke-rule: API endpoints must validate input with Pydantic models.
```

### `@pcke-lesson`

Records a lesson learned or design decision:

```go
// @pcke-lesson: We tried LRU eviction but clock-sweep performs better
// under mixed workloads with occasional sequential scans.
```

```javascript
// @pcke-lesson: React.memo on list items reduces re-renders by 60%.
```

## Supported languages

| Language | Comment syntax |
|----------|---------------|
| Go | `//` single-line, `/* */` block |
| Python | `#` single-line |
| JavaScript / TypeScript | `//` single-line, `/* */` block |
| JSX / TSX | `//` single-line, `/* */` block |
| Java | `//` single-line, `/* */` block |

## How annotations are used

Annotations are extracted during `pcke scan` and stored in the knowledge base.
They appear in:

- Context files generated by `pcke sync`
- MCP server responses (via `get_constraints` tool)
- Query results (`pcke query 'type = "rule"'`)
- Full-text search (`pcke recall "database access"`)

## Best practices

- Place annotations near the relevant code.
- Keep annotations concise (one sentence preferred).
- Use `@pcke-rule` for prescriptive constraints ("must", "always", "never").
- Use `@pcke-lesson` for descriptive insights ("we found", "this works because").
